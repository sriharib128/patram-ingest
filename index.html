Engineering Patram 1.5

Agentic data pipelines at cluster scale

The engine that generated the training data for Patram 1.5

Every kind of training data needs its own pipeline of models. Patram-Ingest lets us write any of them as a dynamic graph of agents, where each sample takes its own route, and runs that graph with pipeline parallelism across a shared GPU cluster. Runs grow onto free GPUs and recover from failures on their own, and no result is lost or written twice.

01 The problem

Generating training data with models, at scale

Generating data with a model is simple for one page. With millions of pages, many models and machines that fail, it becomes a distributed systems problem.

Patram 1.5 reads Indian documents: bills, forms, budget tables, scientific papers, phone screenshots. It transcribes them, turns them into Markdown, HTML or JSON, reads their charts and tables, answers questions about them, and says so when a page can't answer what was asked. A model learns each of those skills from examples, and Patram 1.5 needed more than fifty million of them.

We made them with other models. A larger teacher model looks at a page and writes a question, another call answers it, a specialist model transcribes the page, and a checker compares the result against the page. For one page, the whole idea fits in four lines:

for page in pages:
    reply = model(instruction, image=page)
    if looks_valid(reply):
        save(page, reply)

At our scale, that loop runs into four problems.

  1. One call is never enough. Each kind of data needs its own chain of models, and different pages need different chains.
  2. One machine is far too slow, and too small. The work has to spread over dozens of machines, and a single pipeline can use more models than one machine can hold.
  3. Machines fail. Over a run that lasts days, processes are killed, model servers crash and machines are taken back.
  4. Many teams share the cluster. Several pipelines run side by side, and most of them want the same models.

Patram-Ingest is that loop, rebuilt to handle all four. The rest of this post takes them one at a time.

02 Dynamic graphs

Pipelines as dynamic graphs of agents

Each kind of data needs its own pipeline, and different pages within it need different steps. One description covers all of them.

Good training data never comes out of a single model call. Ask one model for "a question and answer about this page" and you get the same few easy questions back, a million times. So every kind of data Patram 1.5 learned from has its own chain of models, each doing one narrow job with its own prompt and its own checks:

Questions and answersunderstand the page → pick question types → write questions → answer → verify against the page
Document to HTMLfind the layout → write HTML → fill in images → render in a browser → compare with the original
Knowing when to abstainprofile the page → edit or hide a value → ask about it → judge the answer blind

Writing each of these as its own script means rebuilding the same machinery every time, and a fixed script sends every page through the same steps, even though a chart and a form need different ones.

So we describe every pipeline the same way: as a graph. Each node is a stage, an agent with one job: a model, a prompt and a check, or a browser, or plain code. Each edge says which stage's output feeds which. And the graph is dynamic: after each stage, a routing function looks at what that agent actually produced and decides, for that sample alone, where it goes next. Two pages in the same pipeline, even in the same batch, can take completely different paths.

Defining a graph

A pipeline author lists the stages, what each one runs, and which ones feed which. A stage can wait for all of its inputs or start on any of them, so graphs can branch and merge.

The routing decision is a small ordinary function the author writes. It sees what each finished sample produced and says where that sample goes next: charts to the chart reader, forms to the form reader, blank pages nowhere at all.

Before anything runs, the graph is checked for cycles, unreachable stages and ambiguous routes, so a wiring mistake fails in the first second rather than six hours in. Every output records the exact route its sample took, so any example in the dataset can be traced back through the agents that made it.

Passing results between agents

When a stage saves a result, the result gets an address: a patram:// link that names the file, the byte it starts at and its length. A later stage declares whose outputs it reads and receives exactly those addresses, so it reads just those bytes, from local disk or object storage, and never scans anyone's files. The checker sees the page and the answer it is checking, and nothing else.

If an agent fails a sample, every stage below it marks that sample upstream failed and moves on. The failure spreads through the graph one hop at a time, so no stage waits forever for input that will never arrive.

03 Pipeline parallelism

Pipeline parallelism: running every stage at once

Describing a pipeline as a graph is half the problem. The other half is running a graph of large models over millions of samples.

The usual way to run a multi-stage pipeline is one stage at a time. Run stage one over every page, wait for it to finish, check it, then launch stage two over everything stage one produced, and so on. It works, but it has three problems at our scale. You see no finished examples at all until the last stage starts. Somebody has to watch each stage and launch the next one, for days. And if you stop halfway, you are left with half-processed data that you can't train on.

Patram-Ingest runs every stage of the graph at the same time. Each stage has its own queue and its own workers, and samples flow through individually: the moment a stage saves a small group of results, those samples join the next stage's queue and are picked up seconds later, while the first stage keeps working. This is pipeline parallelism, the same idea as an assembly line.

Handing samples from one stage to the next is where pipelines usually lose data, so the hand-off follows a strict rule: a stage passes a sample on only after its result is safely on disk. A background check repairs any gap, so even a crash between "finished" and "marked ready for the next stage" is repaired automatically. The mechanism behind this is in the optional deep dive at the end of the next chapter.

04 Many machines

Running one graph across many machines

Each stage runs on whichever machine holds its model, and samples move between machines through the stage queues.

If every agent in a pipeline fit on one machine, none of this would be hard. Load all the models into one program, pass each page from one function to the next, and the routing would be a few nested if statements. Plenty of pipelines start exactly like that.

In practice the models are large. A larger teacher model needs several GPUs to itself, and the chart reader, the transcription model and the checker each need their own. A machine has eight GPUs, and a pipeline can need more than eight just to hold its models, before adding any copies for speed. At that point the pipeline no longer fits in one program.

So Patram-Ingest lets the stages of one graph live on different machines, and makes those machines behave like one. Each stage runs wherever its model is, pulling from its own queue. When a sample finishes one stage on one machine, it lands in the next stage's queue, and whichever machine runs that stage picks it up. The sample travels across the cluster, but no machine needs to know where the next stage runs, and neither does the pipeline author: the graph file is the same whether it runs on one machine or ten.

Results need care when they cross machines. A stage reads the earlier results it needs by their patram:// address, and the engine knows whether that address is readable from the machine asking: a result still sitting on one machine's local disk is only handed to that machine, while results on shared storage can go anywhere. Results move to shared storage on their own, in the background, and a result is never published before everything it refers to has moved too. None of this shows up in the pipeline itself.

Models are shared across machines too. When several stages use the same model, they send their requests to a single shared copy instead of each loading their own, so a pipeline with three teacher-model stages still needs only one teacher.

The problem

The stages of one graph run as separate processes, often on separate machines, and they share nothing in memory. A graph can also do three different things: send each sample down a branch chosen by what it contains, wait for several inputs before starting, or both at once. We wanted one mechanism that covers every shape of graph, so that no pipeline ever needs special wiring.

The router ledger

Every stage in a graph gets a position, like a seat number. For each sample that is in flight, the router keeps one row in Postgres holding two numbers. Each number is a row of on/off switches, called bits, one per stage:

  • Finished: which stages have finished this sample.
  • Ready: which stages have been marked ready for processing on this sample, meaning it is now waiting in their queue.

That is the whole ledger. Branches and merges are both worked out by looking at these two rows of switches. Here is one sample's row as it crosses the example graph:

finished ready for processing just changed

1. Understand finishes. The sample has just entered the graph. Understand is the first stage, so it was marked ready at the start.

UnderstandChartsQuestionsVerify finished ready

2. Routing picks a branch. Understand's routing function says this page is a chart. The sample goes straight into Charts' queue, and the ledger marks Charts ready.

UnderstandChartsQuestionsVerify finished ready

3. Charts finishes, the sweep notices. Questions is set to start as soon as any one of its inputs is done. Within five seconds a background sweep sees the new switch and marks Questions ready.

UnderstandChartsQuestionsVerify finished ready

One call per hand-off

When a stage finishes a batch, it makes a single call to its router coordinator (every stage process has one). The call does the same things in the same order every time:

  1. If the stage has a routing function, ask it where each sample goes next, and put each sample straight into the queue of the stage it chose. This is how every sample picks its own path, and it happens immediately.
  2. Switch on the stage's finished bit in the ledger.
  3. Switch on the ready bits for the stages that were just handed samples.

So a stage gets work in one of two ways. A routing decision hands it a sample at once, based on content. Otherwise the sweep does, which brings us to merges.

How merges work

A stage that waits on several inputs doesn't receive a message from them. Instead the sweep, a single background process, reads the ledger every five seconds. For each waiting stage it asks: have all of its inputs finished this sample, or any one of them if the stage is set to start on any? If yes, it marks the stage ready. Because it only reads the ledger, it doesn't matter which machine ran which input, or in what order they finished.

Why this works across machines

No stage ever talks to another stage. Each one reads its own queue and writes to the next stage's queue and to the ledger, and all of that lives in Postgres. A stage can therefore run on any machine that can reach the database, and moving it to a different machine changes nothing in the graph. It is the same property that lets machines join and leave freely, which the next section shows.

Crash safety at the hand-off

The order of the writes matters. A sample goes into the next stage's queue first, and the ledger says ready only afterwards. If a process dies between the two, the ledger still shows the stage as not ready, so when things restart the sweep's very first pass sees the gap and marks the stage ready again. Doing a write twice is harmless, because every write is built so that repeating it changes nothing. It is the same "save first, then mark it done" rule the crash chapter describes, applied between stages.

Checked before anything runs

At startup the router checks the graph for cycles, for stages nothing can reach, and for any stage reached by both a routing decision and a merge, because those two mechanisms must never overlap. That separation is why one code path handles every graph shape.

Ledger size

A sample's row is deleted once it has finished every final stage, so the ledger only holds samples that are in flight, never the whole dataset.

05 Distribution

Distributing work through a Postgres queue

Machines don't talk to each other or to a coordinator. Each one takes work from a shared queue.

Each stage needs many machines working on it, so something has to decide who does what. If two machines take the same sample, we pay for it twice and train on a duplicate. If a sample falls between them, it is never done. The usual answer is a coordinator process that hands out work, which is one more process that can crash and take the whole run with it.

We use a database table instead. Each stage's queue is a table in Postgres with one row per sample, and every row has a state: waiting, working, done or failed. A machine that wants work sends the database one request that picks a few waiting rows, marks them working and writes its own name on them, all in one step.

Postgres's SKIP LOCKED makes this safe. Postgres locks each row as it's picked, and a second machine making the same request at the same instant skips those rows and takes the next free ones. Two machines can never get the same sample, and neither waits for the other.

That table is the entire coordination mechanism. Nothing is assigned in advance, so a fast machine simply takes more work than a slow one. To grow a run, start the same program on more machines; to shrink it, stop some.

The database is deliberately simple: ordinary Postgres on the local SSD of one fixed machine. We considered replicated databases, in-memory stores and a database that moves to whichever machine starts first, and turned each down because each added a new way to fail. The cost of this design is small: taking a batch takes milliseconds against tens of seconds of model work, so the database is about a thousandth of a run's time, and a queue of a hundred million samples fits on one disk.

06 Crash safety

Recovering from a crash without losing or repeating work

On a shared cluster any process can die at any point, so recovery has to be correct wherever the crash lands.

Processes die for every reason there is. One runs out of memory, a colleague needs a machine back, a GPU process hangs and has to be killed, the power goes. So we built the engine assuming any process can vanish between any two lines of its code, and for every line that changes something, we made sure a restart handles a death just before it, in the middle of it, and just after it.

For saving results, all of that comes down to one rule, the same one a careful person follows with a to-do list: save it first, then mark it done. A result is written safely to disk, and only after that is its sample marked done in the queue.

Any machine can die at any moment. When it restarts, at most one small group of work is redone, and no result is ever lost or written twice.

When a machine comes back, its restart applies the rule mechanically. It hands back every sample it had taken but not marked done, and it trims from its output file any result the queue never marked done. One consequence is that a result can be complete and safe on disk and still be thrown away, if the crash came a moment before it was marked done. That is deliberate: the queue is the single source of truth, so files and database can never disagree and nobody ever reconciles anything by hand.

Saving happens in small groups, by default 250 results at a time, because forcing data onto a network disk is slow and doing it for every single result would spend more time waiting than computing. The group size is a dial: one disk write and one database update per group, and never more than one group to redo after a crash.

07 Errors

Error handling: the sample's fault or the system's

At this scale, rare errors happen often. Handled carelessly, they silently remove good samples from the dataset.

Run tens of millions of samples through dozens of models for days, and a one-in-a-million event happens dozens of times. Images are corrupt. Models return broken JSON or stop mid-sentence. Servers crash, sleep, run out of memory or answer slowly. Networks blip, disks fill up, databases fail over.

The risk is in how an error is handled. If a model server dies and every request after it is simply counted as a failed sample, the run marches through millions of perfectly good samples and marks them all failed, and the dataset ends up with a hole nobody can explain. So every error in Patram-Ingest is caught where it happens and answers one question: is the sample at fault, or the system?

When an error is ambiguous, the engine blames the system. The two mistakes don't cost the same: blaming a good sample is permanent, while blaming the system costs a retry, and if failures keep coming with no successes at all, a fuse stops the run with nothing lost. The result is a dataset where every missing sample has a recorded reason, and none are missing because of an outage.

08 Scaling and recovery

Automatic scaling and recovery

Pipelines follow whichever model servers are running, so a run grows onto free GPUs and recovers from failures without anyone watching it.

Our runs last days across dozens of machines. Something breaks every hour, and GPUs free up and get taken back all the time. A small team can't be on call to restart a stage, move work off a dead machine or launch more workers when a node frees up, so the engine does two things by itself: scale to whatever GPUs are free, and recover whenever something fails.

Both come from one decision: pipelines don't own models. The cluster hosts model servers on every machine, restarts any that crash, and checks every server with a known test image before trusting it. A registry always knows which servers are serving right now. Pipelines are lightweight and own no GPUs at all. Every 30 seconds a pipeline reads the registry, starts a worker for every server that is serving, and retires the worker of any server that has gone. Scaling and recovery both follow from that loop.

  • More GPUs, more workers. Bring a new machine's servers up and every pipeline spreads onto it within a minute. You can even launch a run before any model is up: it waits, and starts the moment a server appears.
  • Fewer GPUs, no failures. When a server goes away, its worker drains: the requests it was holding go back to the queue without counting against any sample, and other servers pick them up.
  • One model, every team. Since nobody owns a server, any number of pipelines from any team share the same hosted models instead of each starting their own copies.

Borrowing GPUs from a running job

Someone who needs a few GPUs for a quick experiment used to have two options: kill a big production run, or wait days for it to finish. Now they put the servers on a few machines to sleep. A sleeping server gives back almost all of its GPU memory in seconds. The run notices the servers are gone, drains its in-flight requests on those machines and carries on everywhere else. When the experiment is done, the servers are woken, and the run picks them back up within seconds, by itself.

One detail made this work in practice. To decide whether a server is alive, a natural check sends it a small test request. On a busy server, that test waits in line behind hundreds of real requests, so healthy, busy servers look dead and the run backs off them for no reason. The engine reads each server's own token counters instead: if requests are queued and tokens are still being produced, the server is alive, and no test request is needed.

What happens when each part fails

A worker process is killed

Its pool notices within half a second, retries the unfinished requests on other workers and starts a replacement.

A model server crashes

Hosting restarts and re-tests it. Meanwhile its workers pause, and the requests they held go back to the queue without counting as failures.

A server is put to sleep

Its workers drain and retire, and come back on their own when the server wakes.

A machine is killed outright

On restart it hands back the samples it held and trims its files. The other machines carry on in the meantime.

The database fails over

Every connection finds the new primary within a fixed time budget. Work in flight is neither lost nor done twice.

A run needs to stop

One row in a control table asks named machines to stop. They return their work and exit cleanly, and a relaunch resumes exactly where they left off.

Recovery starts with noticing a failure. A dying machine can't report its own death, so the engine never relies on it to. Every sample records which machine took it at the moment of taking, and the database keeps per-machine counters as a side effect of writes that happen anyway. A machine that has stopped producing shows up as counters that stopped moving, and the cluster dashboard reads that with nothing installed on the machines.

09 Any model

Supporting any model backend

Large language models are only some of the agents. The engine treats a browser or a CPU function the same way as a GPU model.

A real data pipeline mixes all kinds of work. Some stages call large models through vLLM, some run a PyTorch model straight from Hugging Face, some run our own models, some drive a pool of headless browsers that render HTML into images, and some are plain CPU code. We didn't want a separate engine for each, so anything that does the work is described by three small functions: how to start it, how to process one request, and how to shut it down.

The engine runs one worker per GPU (or per browser, or per CPU slot), streams each request to the least busy worker the moment it has room, and watches every worker for crashes. Everything above that line, from queues and retries to crash recovery and scaling, never knows which kind of worker is underneath.

Each part of the engine has one job and one interface: the database layer knows nothing about models, the worker pool knows nothing about databases, and the graph layer knows nothing about either. We have rewritten whole layers without touching the ones around them.

10 Using it

What a pipeline author writes

The engine is written once and shared. A pipeline author writes only the prompts, checks and routing.

Everything in the previous chapters, from dynamic graphs and pipeline parallelism to the queue, crash recovery, error handling, scaling and recovery, is written once, in the engine. Without it, every new kind of data would mean someone rebuilding the same machinery from scratch: work splitting, retries, resume after a crash, coordination between machines. Each rebuild would differ slightly, and its bugs would show up days into a run.

With the engine, an author only designs the pipeline: which agents, which prompts, what a good answer looks like, and where each sample goes next. Once that design is ready, it runs on as many machines as are free, with every guarantee in this post.

To run it, you start the same command on every machine. After anything goes wrong, you run the same command again. There is no step for recovery, sharding, retries, coordination or scaling, because those were designed once and are shared by every pipeline the team writes. The same engine ran transcription, HTML conversion, chart reading, question answering, abstention and dozens of other pipelines.

11 Patram 1.5

Generating the Patram 1.5 corpus

Every pipeline behind Patram 1.5's training data ran on Patram-Ingest.

Patram 1.5 was trained on more than fifty million examples, 41 billion tokens in all, and every one of them came out of pipelines built on this engine. Some were a single model call per page. Others were graphs of six or more agents, where a page was understood, routed to specialists, questioned, answered, checked, and escalated to a larger teacher model when the answer fell short.

12 Takeaways

Key takeaways

  1. Write every pipeline as a dynamic graphNodes are agents with one job each, and every sample chooses its route from what the previous agent produced.
  2. Run every stage at oncePass samples along in small groups so finished data flows from the first minutes, and let stages live on different machines.
  3. Coordinate through a tableOne row per sample, taken with FOR UPDATE SKIP LOCKED. No coordinator to crash and nothing to elect.
  4. Save first, then mark doneOn restart, keep only what the record confirms, and ask of every line what happens if you die before, during and after it.
  5. Classify every error by causeDecide whose fault an error is where it happens. A system failure pauses work; only a sample's own failure fails the sample.
  6. Separate model hosting from pipelinesLet pipelines follow whichever model servers are running. Scaling, recovery and sharing models across teams all come from this.
