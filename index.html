01 · The problem

The job that always crashes

Before a vision‑language model can be trained, somebody has to build its dataset. Ours starts as raw document images, and every useful label on them, the OCR text, the caption, the layout boxes, the quality score, is the output of some other model. Each label is one model call, prompt and image in, JSON out, repeated a few hundred million times. We run that on a cluster of 32 nodes, where a node means one machine with 8 H100 GPUs in it. A single pass over the dataset takes days, and it has to finish before training can start.

A job that long on a shared cluster doesn't run cleanly. Nodes get reclaimed by other teams mid‑run. A machine runs out of memory. The database fails over. vLLM, the inference engine under everything, sometimes crashes on its own. During one run, orphaned GPU processes took down a node every ten minutes for six hours.

The hard engineering problem is the restart. After a crash you have output files on one side, a record of what finished on the other, and the crash landed somewhere between the two. Trust the record and you drop work that was already written; trust the files and you process an image twice. Either way the dataset comes out wrong, and nobody notices until training.

Each project on the team used to hand‑write this resume logic, and each version got it wrong in its own way. Patram‑Ingest replaces those scripts with one engine that makes one guarantee.

Kill any process on any machine at any instant, then restart it: at most 250 images are re‑processed, none are lost, and none are written twice.

The machinery behind that guarantee is small: a PostgreSQL table that tracks every image, one rule about the order in which bytes reach disk, worker processes that talk only through queues, and, for multi‑stage pipelines, two extra state values. The rest of the post goes through those pieces in turn.

02 · The core idea

Every image is in exactly one of four states

The engine keeps one PostgreSQL table, images, with one row per image and a state column holding one of four values. At any instant, everywhere in the cluster, an image is in exactly one of these states.

  • 0 · pending“Nobody has picked me up. Please process me.”
  • 1 · processing“A worker somewhere already owns me. Don't touch me.”
  • 2 · done“My output is written. Never send me anywhere again.”
  • 3 · failed“I can't be processed by this pipeline, and retrying won't change that.”

Most of the machinery in later sections exists to keep that sentence true while processes are being killed around it. Here is one image going all the way through.

When a node needs work, it takes a batch of pending rows and flips them from 0 to 1 in one atomic statement, using FOR UPDATE SKIP LOCKED. If 24 nodes ask at once, each gets a different batch; a row can't be half‑claimed, and two nodes can't both win it.

That claim query is also the entire multi‑node coordination. Every machine points at the same table and runs the same program, so a new node starts claiming work and a reclaimed one simply stops. There is no leader, no membership list, and no node‑to‑node channel to repair after a failure.

A central database sounds like a bottleneck until you put numbers on it. Fetching 200 rows takes 5–10 ms, while running those images on a GPU takes 20–30 seconds, and at 100 million rows the database is roughly 20 GB. One Postgres instance on local NVMe handles that easily. It is a single point of failure, and we accepted that because it fails in an obvious way.

The distributed options we rejected side note

We considered rqlite and LiteFS for replicated SQLite, Redis as a work queue, and a scheme where the first node to boot hosts Postgres for the rest. Each added a membership or failover problem to a cluster whose nodes can be reclaimed during a run.

The workload never justified that cost. Each node sends one 5 ms query about every 25 seconds of GPU work, so a single unreplicated Postgres instance answers the useful part without becoming part of the bottleneck.

03 · The machine

From a claimed path to a durable result

Now every node can see the same pending images and claim work without colliding. The next problem starts on the node: turn those claimed paths into output, get that output safely to disk, and only then say the image is DONE.

Six components handle that on each node, split across two kinds of process.

  • recoveryRuns before work starts. It checks the active shard against PostgreSQL, trims any incomplete tail, and returns replayable work to its fetch state.
  • preparationBuilds the prompt, checks that the image can be read, and creates the small request the worker needs.
  • workerRuns vLLM, a browser renderer, or another Python function. It is the only component that touches a GPU.
  • collectorChecks the response against the job's rules: parseable JSON, valid structured output, or a usable rendered result. It sends eligible failures back for retry and returns either validated output or a terminal failure.
  • writerWrites validated results to a JSONL shard, fsyncs the file, and makes the result durable.
  • orchestratorOwns the lifecycle and row transitions. A durable result becomes DONE; an image that has exhausted its valid retries becomes FAILED.

The writer commits in groups of 250: write the output, fsync it, then mark the matching rows DONE. On startup, recovery checks only the last, possibly incomplete group of 250 against the database, trims it, and returns those rows for replay. That check costs the same whether the run has processed ten thousand images or a billion.

The process split keeps the hot path simple. Preparation, collection, writing, and recovery share one CPU‑only Python process, where threads can overlap prompt building, validation, and disk I/O. The worker runs in a separate process, so the model's Python bookkeeping doesn't compete with that work for the same interpreter.

Every component has one job. Workers never change a database row. The collector decides whether an answer is usable. The writer decides when the JSONL record is durable. The orchestrator moves the row only after those decisions are made. That separation is what lets the pipeline recover without every component carrying its own idea of the run's state.

Ctrl+C and SIGTERM take the pipeline through the same shielded teardown: stop accepting work, reset in‑flight rows, close the writer, and stop the workers. The multi‑stage layer in section 08 reuses this exit path unchanged.

04 · Durability

Where the 250 comes from

The table tracks who owns each image. The remaining question is when a result is safe enough to mark DONE, and the answer is an ordering rule inside the writer.

The writer thread buffers results, and every 250 records it runs one fixed sequence: append to the shard file, flush and fsync so the bytes are on the drive rather than in a buffer the kernel might lose, and only then mark those rows DONE in the database.

Data becomes durable before anything records that it exists. With that ordering, a crash at any point can leave work to redo, and can never leave work that was recorded but lost.

The 250 itself is a config value, and any other number works; lower it and the replay window shrinks further. What sets it for us is where the fsync lands. Our shards live on a shared FSx Lustre mount, where an fsync can stall for 50–500 ms and every call adds load to a filesystem the whole team is using, so we commit in groups of 250 rather than hammering the mount with smaller, more frequent syncs.

On restart, recovery truncates the active shard back to the last committed boundary, resets any row still sitting at PROCESSING, and carries on. The panel below walks through each place a crash can land and what it costs.

Kill the model server often enough that the engine gives up, and the run aborts under a named reason with its 12 in‑flight rows handed back and nothing marked FAILED. Both test harnesses run on a laptop with no GPU, because none of this logic knows a GPU exists.

05 · Failure meanings

Four outcomes, four actions

The write‑fsync‑mark order protects output once it exists. It can't tell us whether an answer is usable, whether an image is bad, or whether the model ever answered at all, and treating those as one failure is how a single dead backend marks millions of rows FAILED. So every request comes back tagged with one of four meanings, and the next action follows from the tag.

ok the answer passed

The model answered and the collector validated it. The writer can commit it, then the row becomes DONE.

fail the answer is unusable

The model answered, but the output fails validation, most often because it is not valid JSON. Retry it on a bounded budget; then mark the image FAILED.

reject the input cannot work

The image is missing, corrupt, oversized, or deterministically refused. Mark it FAILED now. Another attempt cannot change the input.

infra nothing answered

The server died, the worker was killed, or the port vanished. Keep the image replayable and stop the run if the infrastructure stays unhealthy.

The split follows who can know what. The worker holds the backend connection, so it tags a deterministic input rejection or a dead backend. The collector sees the returned text, so it decides whether an ok response is valid or a retryable fail. The orchestrator owns retry budgets and database rows, so it applies the state transition.

Before that split, all four outcomes became None. The pipeline retried three times against a dead server, marked the image FAILED, and moved on. A single crashed backend could then march ten million rows into the failure state at full speed, leaving a finished run that looked exactly like the model had rejected every image on its merits.

infra gets its own path because the image has done nothing wrong. It is retried under a separate budget and never becomes FAILED, and a run with too many consecutive infrastructure failures aborts with its in‑flight images replayable. The same fuse catches a server that is alive but answering everything badly. The invariant all of this maintains: a FAILED row describes the image, never the machinery around it.

06 · The worker manager

Many workers, one queue

The infra tag only works if something reliably notices that a worker died. Getting that right forced a rewrite of the worker pool, and the rewrite is worth walking through because the bug it fixed is easy to ship.

One worker means one model on one GPU, and a node has eight. So the manager runs several, and what a worker is stays open: replicas of one vLLM engine, several Hugging Face models, or plain Python functions. We run pools of 32 headless‑Chrome renderers through the same machinery, because from the manager's side a browser is just a worker whose startup function launches Chrome.

The first version fed them the obvious way: one shared request queue that every worker calls get() on. Load balancing comes free, since whoever finishes first takes the next item, and it's the pattern the standard library's documentation shows.

The problem appears when a worker is killed. mp.Queue.get() takes the queue's internal reader lock while it polls the pipe, and a process killed inside that window never gives it back. CPython has no recovery for a lock abandoned by a dead process. Every surviving worker then blocks on get() forever.

The stall is hard to spot because everything reports healthy. The pool notices the death, recovers the dead worker's in‑flight requests, respawns it, and reports the service fine, while throughput sits at zero with clean logs. We reproduced it in about 20 lines of plain multiprocessing with none of our code involved: with two workers, 3 stalls in 8 kill trials.

beforeshared queue

Three processes contend for one lock, and nothing releases it when a holder dies.

afterprivate inboxes

One consumer, and a killed worker can only poison the inbox nobody else reads.

The fix was to stop sharing the queue. A single dispatcher thread inside the worker manager became its only consumer, handing each request to a specific worker through a private inbox belonging to that worker alone. No two processes contend for anything, so no process can strand anything.

The single‑consumer design fixed more than the bug. Once one process is the only thing talking to the queue, it knows exactly which requests each worker holds, in ordinary Python, in its own memory, with no shared ledger and no cross‑process bookkeeping. Several things we'd wanted on the worker side turned into local code:

  • Liveness by asking the operating system. The manager owns every process handle, so detecting a hard kill is proc.is_alive() every half second. Around 30 seconds became under one.
  • No dangling work. When a worker dies, the manager emits one infra response for every request it owed, so nothing upstream waits on an answer that isn't coming.
  • A policy per pool. respawn for cheap independent workers, where one death costs throughput. abort for vLLM, where a death is usually an out‑of‑memory or driver fault that respawning just reproduces while burning GPU‑minutes invisibly.
  • A cause of death in words. When a pool aborts, the reason reads like all 8 workers dead; last: rank 1 died before startup finished; respawn budget exhausted, instead of a flag.
  • Capacity‑aware dispatch. The manager knows each worker's load, so the next request goes to the least busy one instead of wherever the queue happened to put it.

It also deleted code. The worker‑side semaphore, the shared in‑flight ledger and the write‑ordering rules around it all existed to manage sharing that no longer happens.

07 · Throughput

Two things starved the GPU

With correctness settled, the remaining question is whether the GPUs stay busy. The first implementation was the obvious loop, build a batch of prompts, call vLLM's LLM.generate() on it, validate the results, repeat, and it left the GPU idle for two separate reasons.

First, the GPU was waiting on prompt preparation. Before a single image reaches the model you have to read it off disk, decode it, and run the model's own processor over it. There's no reason the GPU should sit through that, so we overlapped it: while the model works on batch N, prepare batch N+1. Threads came first and bought little, since the interpreter runs one at a time, so preparation moved into its own process and the two sides talked over an mp.Queue.

That was faster, and it surfaced a new stall. A decoded page can be 10 MB or more, and a queue moves a message by pickling it into bytes and copying those bytes through a kernel pipe. At roughly 1.7 ms per item per direction, on a full batch, in the gap between two generate() calls, the GPU was now idle waiting for pixels to finish moving between processes. The fix was to stop moving them.

How the shared‑memory handoff works side note

A queue's job is to move a message between two processes. put() pickles your object into bytes and writes them into a pipe; the other side reads the bytes back and unpickles. For a small dict that is microseconds of work. For a decoded 12 MB page it is a 12 MB copy through the kernel on the way in, and another on the way out, for every image in every batch.

Shared memory removes the copy by removing the journey. Both processes map the same block of physical RAM at startup, and we carve that block into fixed‑size slots. To send a prompt, the sender claims a free slot, writes the payload into it, and puts the slot number on the queue. To receive, the worker reads that number, reads the payload directly out of its own mapping of the same physical pages, and releases the slot back to the free list.

The queue is still there and still doing what queues are good at, carrying a tiny message. What changed is that the small integer travels and the 12 MB stays exactly where it was written. The only new bookkeeping is the free list, plus one rule: a slot is released only once the receiver has finished reading it.

Second, one slow item held up everything batched with it. generate() takes a batch and returns when the last sequence in it finishes. If one item out of 64 is slow, or the model is hallucinating its way toward the token limit, the other 63 answers are already complete and sitting in memory, unreturned. The batch on the GPU drains toward empty, and nothing new is allowed in until the call comes back.

Why we also ship the HTTP backend side note

Running a model in‑process is supposed to match running it behind vLLM's own HTTP server with the same engine arguments. It doesn't, and the gap cost us output quality before we found it. Reading vLLM's installed source turned up three mechanisms, each confirmed with a probe script.

A silent scheduler downgrade. The in‑process engine defaults its usage context to a value that isn't a key in vLLM's hardware‑tuned defaults table, so the lookup falls through to max_num_batched_tokens=2048, max_num_seqs=128. On the same H100s the HTTP server picks 8192 and 1024. That is an 8× concurrency loss which never appears in your own config.

Sampling defaults nobody applies. A model ships its own generation_config.json, and vLLM merges it in the HTTP layer, never in the engine. Offline callers silently run at top_p=1.0, top_k=0 while the server honours the model's 0.95 and 64.

Byte‑identical output isn't reachable anyway. The kernels aren't batch‑invariant, so floating‑point reduction order depends on which requests happen to be batched together. Matching the scheduler and the sampler is the achievable goal; exact equality is not.

We fixed all three on the in‑process path, and we also made vllm serve a first‑class backend of its own: the engine can launch a local server and drive it over HTTP, so any engine option works by naming it in the model's YAML with no code change. Choosing between the two is one config value, and both now run identical prompt templating using vLLM's own renderer rather than two implementations that agree by luck.

08 · Multi-stage pipelines

When one model isn't enough

Everything so far is one prompt through one model. Real datasets usually need more: our document pipeline runs six stages over three models, read the page layout, generate structured HTML from it, fill in placeholder images, render the result in a headless browser, translate it, verify it. Supporting that brings a set of requirements.

  • The shape is a directed acyclic graph, not a chain. Stages fan out and merge.
  • A merge stage might need all five of its upstream stages to have finished an item before it can touch it. Another might need any one of three.
  • Some paths are decided at runtime. A tagging stage looks at what it found and sends this image for captioning, that one for entity extraction, and a third nowhere at all. A downstream stage cannot know in advance whether an item is even coming, so it cannot simply wait.
  • Nothing may starve. While stage three works on image n, stages one and two must already be on n+1 and n+2. Every stage runs all the time, or you have paid for eight GPUs to watch one of them work.
  • The models don't all fit on one machine, so this has to hold across nodes while behaving like a single machine.

The usual answer to that list is a workflow engine, with a scheduler, a task graph, leases, and a control plane. Patram‑Ingest covers it with two additions to what the previous sections already built.

Answer one

Two more states in a table we already had

We added 4 UPSTREAM_READY and 5 UPSTREAM_FAILED to the state machine.

A downstream stage is now an ordinary stage that fetches rows at state 4 instead of state 0. That single number is the only difference between a root stage and a middle one.

Answer two

A router with its own small database

One table, one row per in‑flight item, and two integers on it. Bit i of done_mask is set when stage i has finished that item; bit i of the second mask is set when stage i has been told about it.

Every stage declares its upstreams and whether it needs all or any of them, which compiles to a required bit pattern.

The two extra states are what buy pipeline parallelism. Every stage runs continuously, fetching whatever is ready in its own table and sleeping a second when nothing is, so stage three works on image n while stage one is already on n+2. That overlap falls out of each stage independently asking its own table for work; no code schedules it. The router decides when a row becomes ready.

Activation runs at two speeds. A stage that finishes a batch registers those items and, if it has a routing function, writes the chosen rows straight to state 4 in the target stages' tables and sets its own bit, so runtime decisions take effect immediately. Ordinary graph edges use the other speed: a sweep reads the masks every few seconds, compares each stage's required pattern, and activates whatever became ready. Once an item's mask covers every terminal stage, its row is deleted, so the router table is sized by what's in flight, not by the dataset. A hundred‑million‑image run keeps a few thousand rows in it.

Crash safety is the same rule as the writer, one level up. Write the downstream rows first, then set the bit that records you did. Die in between and the bit is still clear, so the next sweep repeats the write, which changes nothing because the update is guarded on the row still being at state 0. Reverse the order and a crash leaves the router believing a stage was activated when it never was, and that item is never processed by anybody, silently, for the rest of the run.

A stage doesn't know it's in a DAG. It fetches rows at a state number and writes results, exactly as it would standing alone. The router doesn't know what an image or a model is. It sets bits and compares them to patterns. Neither imports the other's types, and the hard problem lives in the gap between them, where it is about ten lines of bit arithmetic.

Two smaller things that separate this from a demo side note

Shared models. Stages that use the same model can name the same initialization source and share one loaded copy, so the verify stage reuses the HTML generator's already‑running server instead of claiming two more GPUs that don't exist.

Lineage in the data. Every output record carries the ordered list of stages it went through. When items take different paths, that history lives in the dataset rather than in someone's head.

How a stage reads output written on a different machine side note

Stages don't all run on the same node, so stage two often needs output that stage one wrote to another machine's local drive. Instead of a service that tracks what lives where, the address goes in the database row itself: which shard file, the byte offset inside it, the length, and which node wrote it. One function turns that into bytes, doing a ranged read from object storage if the shard has been uploaded and a direct read at that offset if it is still local.

Uploading a shard so everyone can reach it is four steps in a fixed order: copy it up, record the new location, repoint the rows that name it, and delete the local copy last. While the local file still exists the work counts as unfinished, so a crash anywhere in the middle just means the next sweep does it again.

The repointing step only matches rows still naming the path this node wrote, and that turns out to be the entire safety argument for a machine coming back from the dead. If a node is presumed lost and its unfinished work is handed to others, those rows now name different paths, so when the original wakes up and finishes its upload sweep it repoints nothing and overwrites nothing. There is no lease to expire and no heartbeat to miss.

10 · Production

Eight million prompts later

The largest deployment so far ran 8.47 million prompts through a 27‑billion‑parameter model, unattended, on a cluster shared with other teams. A supervisor borrowed any node whose GPUs were idle and gave it back the moment its owner appeared. Handing a node back is cheap by construction: the worker gets a signal, its teardown returns the rows it held, and they replay elsewhere with nothing marked FAILED. That willingness to yield is what grew the run from 5 nodes to 24.

Every incident from that run is written down with its cause. Orphaned model processes, each pinning about 76 GB of GPU memory and ignoring polite termination, bled nine nodes dry over six hours before we learned to hunt them. The supervisor also taught us that the test for "safe to move onto this node" and the test for "must move off it" are two different tests; the first version used one predicate for both and evicted four healthy workers.

Hardening since then is validated the same way, by hostile testing: the 136 kills in the panel above came from a thread killing a Postgres backend every 1.2 seconds under a live 4,000‑item run, which finished 3,999 done, 1 failed, zero duplicates, zero rows stranded. The database also became the control channel, since the connection string is the one thing every operator, dashboard and node already shares. Write a row into a control table and the node it names stops through the same graceful path as Ctrl+C, a path we'd already spent a year testing.

Where it earns its keep

  • Days‑long GPU inference over 100M+ items, where crashes are certain and a bounded replay is the difference between an incident and a log line.
  • Teams where the person with the prompt shouldn't need to own Postgres, retries or GPU scheduling.
  • Mixed workloads: vision models, text models, browsers and detectors on the same rails with the same guarantees.
  • Shared clusters, because yielding a node costs the owner nothing and the run nothing but time.

Sharp edges we chose

  • No automated test suite. Correctness is validated by kill‑harnesses and real runs, and that trade is written down where every user will read it.
  • A hard kill on a worker strands a bounded number of rows at PROCESSING until that worker's next startup resets them.
  • One Postgres is a single point of failure, accepted in exchange for an obvious failure mode.
  • The response queues keep a small window of the same lock bug the request queue was cured of.
  • A routing target that only ever receives some items leaves the rest parked in its table, which is documented rather than fixed.

11 · Takeaways

If you're building something like this

  • Give every decision exactly one owner, and pick the component in a position to know.

    The worker holds the socket, so it names the failure. The orchestrator holds the rows, so it spends the retries. The manager holds the process handles, so it decides who is alive. Most of the complexity in this system dropped away once each question had one owner.

  • Make data durable before anything records that it exists.

    Write, fsync, then acknowledge. The ordering means a crash can only ever create work to redo, and a fixed boundary means recovery costs the same after any disaster. The same rule applied to cross‑stage handoff is what makes branching pipelines restartable.

  • Never let one return value carry two meanings.

    "The server is gone" and "the model said no" both arrived as None, and that single ambiguity was enough to turn one outage into ten million false failures.

  • Look for the representation that makes the hard case stop being special.

    Two extra states turned every downstream stage into an ordinary stage with a different fetch number. Two integers turned every graph topology into the same bit test. Neither is clever; both replaced a scheduler we would otherwise have had to write and maintain.
